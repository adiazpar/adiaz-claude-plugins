# Migration plan: re-discipline 0.7 to 0.8

Status: Draft for implementation

Target release: 0.8.0

Related RFC: ../rfcs/0001-campaign-state-engine.md

Amendments: ../rfcs/0002-delivery-plan-amendments.md — amends implementation
order (knowledge plane ships additively before the cutover), makes legacy
normalization demand-driven with live-campaign-only exhaustive certification,
narrows enforcement to hook-gated writes, and gates archive opt-in on
measurement. Where this plan and the amendments conflict, the amendments
govern.

Migration style: one hard product cutover with previewed, resumable project
conversion

## 1. Purpose

This plan turns the 0.8 campaign-state RFC into an executable migration. It
covers both halves of the release:

1. changing the plugin so every new operation follows the 0.8 model; and
2. converting existing projects without losing claims, evidence, work
   branches, review decisions, or retrieval behavior.

The migration is not complete when files merely occupy new directories. A
project is migrated only when a fresh agent can accurately traverse every
substantive claim to its supporting evidence, obtain better bounded context
from retrieval, and perform that workflow through both supported hosts.

## 2. Settled product decisions

The migration implements these decisions without compatibility shims:

- 0.8 is a hard release. The checkpoint-campaign and promote-truth skills,
  legacy report stamping, master-file mutation, and legacy workspace writers
  disappear from the shipped plugin.
- The explicit migrator is the only 0.8 component permitted to read 0.7
  structures. It never creates new 0.7 state.
- Files remain canonical. Search databases, embeddings, graph projections,
  generated state views, and context leases are derived and rebuildable.
- The state engine is host-neutral. MCP and a local CLI are peer adapters over
  the same commands, validation, authorization, and result schemas.
- State mutations use short transaction locks. A campaign is never locked for
  its lifetime, and read-only retrieval is not serialized behind writers.
- Findings use YAML frontmatter and readable Markdown bodies. One file owns
  one independently reviewable and supersedable claim.
- Every substantive returned run is curated. Curators prepare packets of
  related findings; managers ratify each finding through an individual
  decision receipt.
- Manager-ratified active findings are searchable by managers across
  campaigns with an explicit campaign-provisional label.
- Ratification during an active campaign does not change docs/truth. Truth
  projection occurs only in the campaign closure transaction.
- Migration starts with an exact read-only preview. The user or manager must
  approve the preview digest before canonical conversion begins.
- Conversion builds and verifies a shadow representation before any physical
  reorganization.
- A migrated project contains no active compatibility wrappers or legacy write
  paths.

## 3. Scope

### 3.1 Plugin source

The release changes:

- skill inventory and instructions;
- agent definitions and role contracts;
- hooks and mutation boundaries;
- MCP tool schemas;
- the shared state engine;
- the CLI adapter;
- canonical schemas and templates;
- retrieval indexing and ranking;
- benchmark and calibration tools;
- project initialization and migration logic;
- package, integration, and host-conformance tests.

### 3.2 Project state

The project conversion includes:

- project profile and configuration;
- manager adapters;
- active campaigns;
- legacy subagent workspaces and reports;
- manager-produced evidence and scripts;
- open and deferred branches;
- review records;
- docs/truth;
- docs/history;
- backlog records;
- benchmark cases and accepted retrieval profiles;
- derived knowledge indexes.

Source code and ordinary project files are not relocated by this migration.
Only re-discipline-owned state and payloads are reorganized.

### 3.3 Out of scope

This plan does not:

- reinterpret project source files as campaign payloads;
- declare unsupported claims true;
- discard evidence because it is large or inconvenient;
- silently repair contradictions;
- preserve 0.7 commands as deprecated aliases;
- require MCP availability for local project access;
- certify a project from a sample when any substantive campaign content
  remains untraversed.

## 4. Migration state machine

Each project records one monotonic migration state:

1. legacy
2. inventoried
3. shadow-indexed
4. normalized
5. physically-reorganized
6. traversal-verified
7. migrated

The migration journal records each transition, its input digest, output
digest, actor, adapter, timestamp, validation result, and recovery data.

### 4.1 Legacy

The project still operates under 0.7 semantics. The migrator may inspect it,
but no 0.8 canonical writes have begun.

### 4.2 Inventoried

The exact source inventory and conversion plan have been written. Every
planned source path has a size, byte digest, semantic role, destination, and
proposed disposition. The approved plan digest is immutable for that run.

### 4.3 Shadow-indexed

The engine can search the legacy project through a read-only shadow catalog.
Nothing has moved. This state establishes a retrieval baseline and exposes
unclassified material before normalization.

### 4.4 Normalized

Substantive claims, evidence relations, work items, runs, reviews, and
deferrals have canonical 0.8 records in the staging area. Coverage reports
identify every legacy source as represented, intentionally retained as
payload, or blocked for explicit review.

### 4.5 Physically reorganized

Canonical 0.8 paths are active. Each moved or transformed object has
source-to-destination provenance and byte- or semantic-equivalence checks.
Legacy paths are no longer operational inputs.

### 4.6 Traversal verified

Automated coverage, retrieval evaluation, blinded agent evaluation, and host
parity all pass. Every substantive claim is reachable and every cited
evidence target resolves.

### 4.7 Migrated

The migration receipt is ratified, the 0.8 state head is active, derived
indexes are rebuilt from canonical files, and no unresolved migration blocker
remains.

## 5. Safety and authorization model

### 5.1 Preview before mutation

The preview command is read-only. It produces:

- project identity and detected schema version;
- all in-scope source paths;
- planned record creation and physical moves;
- unresolved classifications;
- conflicts and malformed records;
- expected index and profile changes;
- baseline benchmark requirements;
- estimated payload and record counts;
- a stable plan digest.

The apply command requires the exact digest. If relevant project state changes
after preview, application stops and requires a new preview.

### 5.2 Short locks

A lock protects only a single canonical state transition or bounded batch
commit. Expensive parsing, embedding, evaluation, and curator work occurs
outside the lock against an immutable input snapshot. Commit reacquires the
lock and verifies the expected state head.

Readers continue to use the last committed state while a new batch is being
prepared. A stale writer receives a conflict and must rebase or regenerate its
batch.

### 5.3 Dirty worktrees

The migrator must operate safely in projects with unrelated user changes:

- it inventories only re-discipline-owned paths;
- it does not reset, clean, stage, or commit Git state;
- it reports overlapping edits before mutation;
- it writes staged conversion output under the migration transaction;
- it refuses an ambiguous overwrite;
- it leaves unrelated files untouched.

### 5.4 Idempotence and restart

Every conversion operation has a stable operation ID and input digest.
Replaying a completed operation verifies its receipt and becomes a no-op.
Interrupted operations resume from the last committed journal entry.

Temporary output is never considered canonical. A state-head swap occurs only
after the entire bounded batch passes validation.

### 5.5 Failure behavior

On failure:

- the last committed canonical head remains readable;
- incomplete staging output is retained for diagnosis or safely discardable;
- the journal records the failed stage and reason;
- no legacy source is deleted;
- no fallback profile is silently accepted;
- the user receives the precise retry or review action.

## 6. Proposed operator surface

The exact executable name may change during implementation, but MCP and CLI
must expose equivalent operations.

### 6.1 Preview

Command:

    re-discipline migrate-project --project PATH --preview

Outputs:

- migration-plan.yaml;
- migration-plan.md;
- source-inventory.jsonl;
- conflict-report.json;
- baseline-retrieval-plan.json;
- plan digest.

This command makes no canonical project mutation.

### 6.2 Approve and apply

Command:

    re-discipline migrate-project --project PATH --apply PLAN_DIGEST

This initializes the journal, records explicit approval, and performs
restartable conversion through physical reorganization. It stops at any
ratification or ambiguity gate.

### 6.3 Resume

Command:

    re-discipline migrate-project --project PATH --resume TRANSACTION_ID

Resume verifies the source snapshot, plan digest, and last committed state
head before continuing.

### 6.4 Status

Command:

    re-discipline migrate-project --project PATH --status

Status reports the current migration state, completed operations, blockers,
coverage, evaluation gates, and safe next action.

### 6.5 Verify

Command:

    re-discipline migrate-project --project PATH --verify

Verify is read-only. It rebuilds indexes in an isolated location, checks
record and evidence traversal, runs the required retrieval suites, and emits a
candidate certification receipt.

### 6.6 Ratify

The manager ratifies the final receipt through the normal state mutation
surface. Ratification changes the project state to migrated; it does not
commit project files to version control.

## 7. Plugin implementation workstreams

### 7.1 Shared state engine

Extract all project operations into one host-neutral engine:

- parse and validate canonical records;
- authorize role-scoped transitions;
- append journal events;
- maintain state heads;
- create deterministic result digests;
- build and query derived indexes;
- compile bounded context cards;
- run migrations and verification.

The engine must not depend on a host transcript, host-specific tool naming, or
one provider's environment variables.

### 7.2 MCP adapter

The MCP adapter presents compact schemas that both supported hosts can render
and invoke correctly. It performs protocol translation only; it does not
contain separate business rules.

Tool responses return summaries, handles, and explicit expansion options.
They do not return full reports by default.

### 7.3 CLI adapter

The CLI invokes the same engine commands and returns equivalent structured
results. It is the local fallback when MCP discovery, startup, transport, or
schema rendering fails.

Given identical canonical state and request input, MCP and CLI results must
have the same semantic result digest. Adapter-specific transport metadata is
excluded from that digest.

### 7.4 Skills and agents

Remove these 0.7 skills from the 0.8 package:

- checkpoint-campaign;
- promote-truth.

Rewrite campaign lifecycle skills around transactional state operations.
Add a migration skill that guides preview, approval, application,
verification, and ratification without bypassing the engine.

Add the knowledge-curator role. Its authority is limited to:

- reading returned runs and provenance;
- drafting atomic finding records;
- linking evidence;
- proposing relations and dispositions;
- assembling review packets.

The curator cannot ratify findings, mutate truth, close campaigns, approve its
own packets, or change retrieval profiles.

### 7.5 Hooks and policy boundaries

Hooks should enforce:

- substantive returned runs enter the curation queue;
- state-changing file edits occur through the engine;
- unsupported legacy write paths fail with a direct migration instruction;
- context expansion respects the active budget or lease;
- truth mutation is rejected outside closure;
- role claims are backed by adapter-issued capabilities, not caller prose.

Hooks are guardrails, not an independent state machine.

### 7.6 Schemas and templates

Add versioned schemas for:

- campaign;
- work item;
- run;
- finding;
- evidence relation;
- intake batch;
- review packet;
- decision receipt;
- event;
- context card;
- closure plan and receipt;
- migration plan, operation, and receipt;
- retrieval profile and benchmark result.

Templates must match the schemas and avoid host-specific language in canonical
project files.

### 7.7 Package removal audit

Release packaging fails if any shipped skill, agent, hook, template, command,
or runtime path can:

- invoke a semantic checkpoint;
- independently promote truth;
- write a legacy CAMPAIGN master file;
- stamp a report as manager-reviewed;
- create categorical workspace folders;
- write a 0.7 record after the 0.8 state head exists.

Documentation may describe legacy inputs only inside the migration guide.

## 8. Project preview and inventory

The preview walks every re-discipline-owned source before proposing changes.
Its inventory is content-addressed so later stages can prove what they read.

### 8.1 Campaign inventory

For each active and historical campaign, record:

- campaign identifier and lifecycle status;
- master-file sections and anchors;
- subagent workspace paths;
- reports and review stamps;
- scripts, analysis, artifacts, and evidence directories;
- manager-owned top-level payloads;
- deferred, blocked, abandoned, and unresolved language;
- references to project source or external evidence;
- duplicate and conflicting reports;
- files that cannot be decoded or classified.

### 8.2 Knowledge inventory

Record:

- truth-file count and sizes;
- claim boundaries per truth file;
- frontmatter completeness;
- validity, confidence, dependency, and evidence metadata;
- history chronicles and surviving reports;
- backlog items;
- indexes and generated caches;
- existing benchmark cases;
- accepted, candidate, dormant, and unsupported retrieval profiles.

### 8.3 Host inventory

Record:

- installed plugin version and source;
- manager adapters present;
- MCP configuration and startup result;
- CLI availability;
- tool-schema discovery results from each supported host;
- project policy and evidence-wall configuration.

### 8.4 Preview blockers

Application cannot begin while any of these remain unresolved:

- two sources would overwrite the same canonical destination;
- a source changes while its digest is being approved;
- a report or truth file cannot be parsed enough to preserve it;
- a proposed record lacks stable provenance to its source;
- an accepted retrieval profile cannot be interpreted;
- a path escapes the project or configured external-object policy;
- the project identity is ambiguous.

## 9. Bootstrap cutover

After plan approval, the migrator creates the minimum 0.8 control plane:

- migration journal and transaction identity;
- schema-version marker;
- state-head record;
- canonical configuration converted from the project profile;
- adapter configuration for both MCP and CLI;
- staging roots for normalized records and payload inventory;
- an immutable snapshot reference to the approved source inventory.

The project remains readable through the legacy shadow catalog while
conversion runs, but all new re-discipline state is written in 0.8 form.
There is no mixed-mode legacy writer.

## 10. Active campaign conversion

### 10.1 Campaign records

Convert each legacy master file into:

- one campaign record for identity, objective, state, policy, and closure
  criteria;
- work-item records for goals, branches, phases, problems, questions, and
  deferred work;
- explicit relations such as blocks, depends-on, derived-from, duplicates,
  challenges, and supersedes;
- event records for recoverable lifecycle transitions;
- a generated state view for human navigation.

The original narrative remains preserved as provenance until physical
verification is complete. It is not used as the canonical state machine.

### 10.2 Phase and tangent recovery

The normalizer detects headings and prose that imply:

- planned later phases;
- follow-up work;
- unanswered questions;
- blocked work;
- abandoned approaches;
- newly discovered branches;
- manager decisions;
- contradictions.

Each candidate becomes a proposed work item or relation. Ambiguous candidates
enter a manager review packet rather than being silently dropped or marked
complete.

### 10.3 Run conversion

Each legacy subagent workspace becomes one run:

- brief and task scope become run inputs;
- report becomes the primary narrative output;
- scripts, captures, binaries, logs, extracts, and analysis become typed
  payload inventory entries;
- manager review becomes a proposed or imported decision receipt;
- timestamps and source paths remain provenance.

A report directory is not created. The run directory is the sole workspace,
and report.md is one role within it.

### 10.4 Legacy folder mapping

Legacy categorical folders are preserved under:

    runs/RUN_ID/payload/legacy/analysis/
    runs/RUN_ID/payload/legacy/artifacts/
    runs/RUN_ID/payload/legacy/evidence/
    runs/RUN_ID/payload/legacy/scripts/

Each retained object receives a typed inventory entry describing its actual
role, media type, digest, producer, and evidence relations. New 0.8 runs write
directly under payload without recreating those categories.

Manager-owned campaign-level evidence or scripts become a manager run when
they represent a coherent attempt. Otherwise they remain campaign payloads
with explicit producer and purpose metadata.

### 10.5 Review import

Legacy review language is imported conservatively:

- a clear manager disposition becomes a proposed imported receipt;
- an ambiguous stamp remains unratified until reviewed;
- a report's self-assessment never becomes manager ratification;
- truth presence does not retroactively ratify every source report claim;
- contradictions remain visible and linked.

## 11. Continuous normalization and curator backfill

### 11.1 Atomic findings

Curators transform substantive report content into finding files with:

- stable finding ID;
- YAML frontmatter;
- one precise claim;
- scope and applicability;
- what the claim does not establish;
- epistemic status;
- durability tier;
- evidence relations with resolvable targets;
- reproduction or verification procedure;
- work-item and run provenance;
- dependency, contradiction, challenge, and supersession relations.

Long reports produce multiple findings. Repeated claims point to one
normalized finding rather than multiplying near-duplicates.

### 11.2 Review packets

The curator groups three to ten closely related findings in a review packet.
The packet gives the manager shared context, conflicts, and recommended
dispositions. The manager records an individual decision for each finding.

Packet review can accept some findings and reject or hold others. Packet
membership never creates bulk epistemic authority.

### 11.3 Cross-campaign visibility

Once a manager ratifies a finding, the index may return it to managers working
in other campaigns. Retrieval must label it:

- durability: campaign-provisional;
- source campaign;
- ratification receipt;
- closure state;
- known conflicts.

Investigators receive active cross-campaign findings only when the manager
includes them in a scoped context pack. They do not automatically inherit the
entire active knowledge frontier.

### 11.4 Coverage accounting

Every substantive source span receives one disposition:

- represented by finding ID;
- duplicate of finding ID;
- non-claim operational narrative;
- retained only as payload;
- rejected with reason;
- blocked for review.

Coverage is measured against source spans and claims, not merely file counts.
Zero unclassified substantive spans is required for traversal verification.

## 12. Truth-record conversion

### 12.1 Storage shape

The preferred 0.8 truth projection is one independently supersedable claim per
Markdown file with YAML frontmatter. Metadata includes:

- truth ID;
- title and claim;
- subsystem or concept tags;
- scope and exclusions;
- status and validity;
- confidence;
- evidence-policy result;
- evidence and verification references;
- dependencies;
- contradictions and supersession;
- source campaign and closure receipt;
- created and last-verified timestamps.

The file body remains human-readable and contains explanation, reproduction,
and bounded provenance.

### 12.2 Splitting legacy truth

A legacy truth file containing multiple independent claims is split only when
the boundaries and provenance can be preserved. If a file already contains
one independently supersedable claim, it may be upgraded in place with
frontmatter and a stable ID.

Large explanation or evidence material may remain in a linked companion
payload, but the claim card must be sufficient for retrieval and
disambiguation.

### 12.3 No new truth during active conversion

Migration may normalize existing accepted truth, but it does not promote
active-campaign findings. New truth projection waits for campaign closure.

When legacy truth conflicts with active evidence, the migrator creates a
challenge relation and retrieval overlay. The truth file is corrected or
superseded only in a closure transaction with full provenance.

### 12.4 Truth compatibility receipt

For every converted truth, verify:

- its claim is semantically preserved;
- all former evidence remains reachable;
- metadata did not increase confidence or scope;
- dependencies still resolve;
- search by legacy title and core concepts finds the new truth;
- any split records retain a relation to their legacy source.

## 13. Physical reorganization

Physical changes begin only after normalization coverage passes and a second
preview shows the exact moves.

### 13.1 Commit procedure

For each bounded batch:

1. verify the source digest;
2. prepare the destination under staging;
3. validate schemas and evidence targets;
4. compare byte digests for unchanged payloads;
5. compare semantic receipts for transformed Markdown;
6. acquire the short transaction lock;
7. verify the expected state head;
8. atomically publish the batch and append its event;
9. release the lock;
10. re-read the published batch through the engine.

### 13.2 Archive destinations

Closed campaigns move to:

    docs/history/campaigns/CAMPAIGN_ID/

The archive retains:

- campaign and work-item graph;
- run records and retained payloads;
- normalized findings;
- review packets and decision receipts;
- event journal;
- closure plan and receipt;
- coverage and migration receipts;
- a generated README view.

The README or chronicle is navigation, not the sole surviving representation.

### 13.3 Source retirement

Legacy paths are retired only after their destination receipts verify. They
may be moved into a transaction-scoped recovery area until final
certification. The release does not maintain aliases from old operational
paths.

## 14. Retrieval and profile migration

### 14.1 Current 0.7 baseline

The migrator records the exact pre-migration retrieval behavior before
changing indexes. The current plugin baseline uses these fusion weights:

- exact: 8
- full-text: 6
- graph: 2
- dense: 4
- reciprocal-rank constant: 60
- rerank depth: 24

Project-specific accepted profiles are inventory, not assumptions. A profile
that the installed runtime cannot support must be reported as unsupported
rather than silently replaced by the plugin baseline.

### 14.2 0.8 retrieval model

Retrieval changes from report- and passage-first search to finding-card-first
search:

1. interpret query class, scope, campaign, and requested durability;
2. generate exact, lexical, and dense finding candidates;
3. fuse candidates using the active profile;
4. apply graph relations after candidate selection for dependency,
   contradiction, challenge, and supersession context;
5. rerank within the requested class;
6. return bounded cards with handles;
7. expand provenance only on request.

Raw reports remain searchable as provenance and migration fallback, but they
do not outrank a valid normalized finding merely because they repeat its
keywords.

### 14.3 Weight conversion

Old numeric weights are not copied blindly because the retrieval units and
graph stage changed. Migration:

- captures the accepted 0.7 profile and its compatibility status;
- runs the old benchmark against the shadow index where possible;
- converts benchmark judgments from path-only targets to stable truth and
  finding IDs;
- establishes a 0.8 baseline profile;
- calibrates only the supported bounded candidate set;
- compares the candidate against both the recorded 0.7 behavior and 0.8
  baseline;
- requires explicit maintainer acceptance before activation.

Until a candidate is accepted, the named 0.8 baseline remains active and its
identity is visible in status and query receipts.

### 14.4 Context budgeting

Every retrieval request declares or inherits:

- result-card limit;
- token budget;
- durability classes;
- active-campaign visibility;
- evidence expansion depth;
- conflict expansion policy.

The engine returns handles and deltas rather than repeating unchanged cards
after compaction. It may say that more results exist, but it may not exceed the
budget without an explicit expansion request.

### 14.5 Cache rebuild

After physical reorganization, verification deletes or ignores all derived
indexes, rebuilds them solely from canonical files, and compares:

- record counts;
- stable IDs;
- evidence edges;
- graph relations;
- query result identities;
- active profile identity;
- result digests across MCP and CLI.

Passing only with the preexisting cache is a migration failure.

## 15. Benchmark and calibration changes

### 15.1 Benchmark corpus

The 0.8 benchmark contains:

- migrated legacy questions;
- finding-level exact lookups;
- subsystem and concept discovery;
- evidence provenance requests;
- contradiction and supersession questions;
- active cross-campaign questions;
- questions that should exclude provisional findings;
- abstention cases;
- bounded-context resume cases;
- closure and history questions.

Judgments use stable record IDs and acceptable evidence targets, not only file
paths or expected keyword snippets.

### 15.2 Required metrics

Measure at minimum:

- recall at configured cutoffs;
- mean reciprocal rank;
- nDCG;
- precision;
- evidence-target accuracy;
- citation resolvability;
- contradiction visibility;
- abstention correctness;
- durability-label accuracy;
- token cost;
- latency;
- repeated-context savings from handles and deltas.

Aggregate scores cannot conceal a zero-recall or unsafe-durability slice.

### 15.3 Calibration

Calibration is performed on a development split and confirmed once on a held
out split. Candidate generation explores the supported weight grid for exact,
lexical, dense, and post-selection graph influence. It also evaluates rerank
depth and context-card limits when those materially affect quality.

The winning candidate must satisfy hard floors before optimization:

- no regression in evidence-target accuracy;
- no provisional-as-truth errors;
- no unresolved citation targets;
- no material abstention regression;
- token use within the configured budget;
- statistically or repeatedly credible improvement on the primary metric.

Calibration emits a candidate profile. It never activates that profile
without an explicit decision.

### 15.4 Stale benchmark handling

Model, embedding, schema, corpus, or index fingerprints are stored with every
result. If any required fingerprint changes, status marks the result stale and
prevents it from certifying migration.

A stale benchmark is diagnostic history, not current evidence.

## 16. Migration certification

Certification has four independent gates. All must pass.

### 16.1 Structural gate

- every canonical record validates;
- every stable ID is unique;
- every relation target resolves or is explicitly external;
- every payload inventory entry resolves and matches its digest;
- every event sequence is internally consistent;
- no legacy write path is active.

### 16.2 Semantic traversal gate

For every substantive legacy claim:

- a normalized finding, truth record, rejection, or explicit blocker exists;
- source provenance resolves;
- cited evidence resolves;
- scope and confidence did not silently expand;
- conflicts and dependencies remain discoverable;
- a query by core concepts can reach the record within the bounded expansion
  workflow.

This is exhaustive. Sampling may help find bugs but cannot replace traversal.

### 16.3 Retrieval and context gate

The 0.8 benchmark passes its hard floors and demonstrates that a fresh agent
can answer the representative project questions with:

- equal or better factual accuracy;
- equal or better evidence selection;
- correct durability labeling;
- fewer unnecessary context tokens;
- no dependence on reading entire campaign masters or report collections.

The evaluation records source IDs opened, context cards consumed, expansion
steps, answer claims, citations, token estimate, and errors.

### 16.4 Host parity gate

Both supported hosts and the CLI must:

- discover the intended surface;
- render valid tool schemas;
- obtain the same project status;
- run representative retrieval and expansion flows;
- enforce role and truth boundaries;
- recover from compaction using bounded state;
- return matching semantic result digests for equivalent requests;
- expose a useful local path when MCP is unavailable.

Core compatibility in one host is not enough if lifecycle instructions,
capability enforcement, error translation, or schema rendering diverges.

### 16.5 Certification receipt

The candidate receipt includes:

- approved plan digest;
- source and destination state heads;
- plugin and schema versions;
- inventory and coverage digests;
- physical equivalence summary;
- benchmark and calibration fingerprints;
- blinded agent-evaluation results;
- MCP, CLI, and host-conformance results;
- known limitations;
- final manager decision.

Only ratification of a fully passing receipt changes the project to migrated.

## 17. Rollback and recovery

### 17.1 Before physical reorganization

Rollback discards uncommitted staging output and derived shadow indexes.
Legacy source remains unchanged. The journal and preview may be retained for
diagnosis.

### 17.2 During physical reorganization

Recovery replays or reverses only the bounded batch described by its receipts.
It verifies exact resolved paths and digests before moving anything. The last
committed state head remains authoritative.

### 17.3 After physical reorganization

The preferred recovery is forward repair from canonical receipts. A
transaction-scoped recovery area may restore verified legacy bytes when a
physical equivalence check fails before certification.

There is no supported downgrade that resumes 0.7 writes after the 0.8 state
head has become authoritative. A hard product cutover is compatible with
recoverable data conversion; it does not require unsafe dual writers.

## 18. Pilot sequence

### 18.1 Small pilot

Use the prelude-pack-recalibration campaign first. The current preview is
approximately seven files, one report, and 27 KB of Markdown.

Purpose:

- validate plan digest approval;
- exercise one complete campaign conversion;
- verify report-to-finding coverage;
- test physical reorganization and rollback receipts;
- debug MCP and CLI parity cheaply.

### 18.2 Large pilot

Use the resource-registration campaign second. The current preview is
approximately 2,395 files, 79 reports, and 1.6 MB of Markdown.

Purpose:

- stress branching and phase recovery;
- exercise large payload inventories;
- prove continuous curator batching;
- test context budgets against a genuinely context-hostile campaign;
- measure traversal completeness and restart behavior;
- expose latency, indexing, and lock-contention problems.

### 18.3 Project-wide truth and history

After both campaign pilots pass, convert docs/truth, remaining history, and
the full project index. Re-run the complete benchmark and blinded
agent-context evaluation before final certification.

Pilot success does not mark the whole project migrated. It only authorizes the
next conversion stage.

## 19. Implementation order and release gates

### Gate A: read-only inventory

Deliver schemas, source discovery, preview artifacts, stable digests, and a
shadow index. Test against representative 0.7 projects without changing them.

Exit condition: repeated previews of unchanged input are byte-stable and
complete.

### Gate B: engine and adapter parity

Deliver the shared state engine, MCP adapter, CLI adapter, capability model,
short transactions, and deterministic result digests.

Exit condition: state and retrieval conformance pass through both adapters.

### Gate C: normalized campaign staging

Deliver work-item, run, finding, evidence, packet, receipt, and event
conversion with curator backfill and coverage accounting.

Exit condition: the small pilot reaches normalized with zero unclassified
substantive spans.

### Gate D: physical layout and closure

Deliver atomic physical batches, directory history, generated views, and
closure-only truth projection.

Exit condition: the small pilot reaches physically-reorganized and can
rebuild from canonical files.

### Gate E: retrieval migration

Deliver finding-card indexing, bounded context expansion, profile conversion,
new benchmark judgments, calibration, and stale-fingerprint enforcement.

Exit condition: the small pilot passes retrieval and context gates without a
silent profile fallback.

### Gate F: scale and restart

Run the large pilot with injected interruption, stale-writer conflict,
malformed input, and MCP outage scenarios.

Exit condition: the large pilot reaches traversal-verified and every injected
failure has a safe, documented recovery.

### Gate G: hard package cutover

Remove all legacy skills and writers, run the package-removal audit, complete
host conformance, and build the 0.8 release artifact.

Exit condition: the artifact contains the migrator's legacy readers but no
legacy writer, wrapper, or deprecated alias.

### Gate H: project certification

Convert remaining project state, rebuild indexes, run exhaustive traversal,
run the full benchmark and blinded evaluation, and ratify the receipt.

Exit condition: project state is migrated.

## 20. Release acceptance checklist

Plugin acceptance:

- 0.8 installs without checkpoint-campaign or promote-truth;
- all mutations route through the shared engine;
- MCP and CLI conformance pass;
- the migrator is the only legacy reader;
- no legacy writer or wrapper ships;
- truth mutation is closure-gated;
- package documentation describes the hard cutover.

Project conversion acceptance:

- the preview digest was explicitly approved;
- source inventory is complete;
- all campaigns and truth records have coverage receipts;
- every substantive claim and evidence relation is traversable;
- physical moves have equivalence receipts;
- active findings carry correct durability labels;
- the accepted profile is supported and visible;
- indexes rebuild from canonical files;
- benchmarks are current and passing;
- blinded agent evaluation demonstrates bounded context improvement;
- both hosts and the CLI pass;
- no blocker remains.

## 21. Definition of done

The migration is complete only when the plugin enforces the 0.8 model and the
project has a ratified migrated receipt.

The decisive test is operational: a fresh agent can ask focused questions,
retrieve compact finding or truth cards, expand exact provenance when needed,
follow every substantive claim to evidence, see conflicts and durability, and
resume the campaign without loading its entire documentary history. That
behavior must be accurate, measurably more context-efficient, reproducible
from canonical files, and equivalent through MCP and CLI.
