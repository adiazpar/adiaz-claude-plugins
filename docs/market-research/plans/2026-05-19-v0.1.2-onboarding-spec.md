# v0.1.2 Spec — Founder Profile Onboarding (`/research-init`)

> **For future implementers:** This spec was written after running the v0.1.1 plugin against a real founder (the author) for the first time. The friction observed in that engagement is the spec.

**Goal:** Eliminate per-command re-prompting for founder profile. Add a `/research-init` slash command that walks the user through a structured onboarding once, writes the result to `.claude/market-research.local.md` (per `plugin-dev:plugin-settings` pattern), and updates the existing seven commands to read founder context from that file before falling back to AskUserQuestion.

**Why now:** v0.1.1's `/research-demand-discovery` (and every other command) requires founder profile + constraints + familiar domains + acquisition preferences. Users supply these per-command. This is high friction and produces bad inputs because:

1. The 3-input prose request is too much at once — users compress to 2, omitting familiar domains (verified in the first real engagement)
2. "Constraints" is too abstract a label — users mix budget choice into constraints; skip acquisition channel; forget time horizon
3. Implicit capabilities (Apple Developer license, AI fluency, existing distribution access) aren't surfaced by open-ended questions
4. "Familiar domains" gets answered with "I want to keep it open" — the most common founder failure mode dressed up as humility
5. Users don't know their acquisition defaults until prompted with concrete options

The right output of onboarding is a **synthesized profile the user reacts to**, not prose the user writes from scratch.

---

## The five friction points from the first engagement

Captured verbatim from the v0.1.1 session that surfaced this spec:

### 1. 3-input prose request was too much at once
The user naturally compressed three asks into two answers, omitting familiar domains entirely. Fix: ask each input as a separate, focused question.

### 2. "Constraints" is too abstract a label
Easier to ask "what won't you do?" and "what won't you spend on?" as separate concrete questions. The user landed budget choice ("go cheap and broad") inside the constraints section instead of the optional add-on slot.

### 3. No prompt to surface implicit signals
The user mentioned having an Apple Developer license almost in passing. That's a real domain-familiarity asset (App Store channel access). The onboarding must directly ask: "What licenses, accounts, or platform access do you already have?" — surfaces real capability filters.

### 4. No anchor to past experience
"Industries you've worked in" wasn't strong enough — should be "industries / problems where you've personally felt pain or sold something." Forces concreteness. The user defaulted to "keep it open" which is the wishlist trap.

### 5. Familiar-domains "I want to keep it open" needs structural pushback
This is the most common founder failure mode. The onboarding should counter it directly with the framing: "industry-fluid is fine; capability-fluid is not." The user IS choosing constraints whether they articulate them or not — their capabilities (engineer + AI agent operator + Apple-licensed + bootstrapped) already scope which problems are feasible. The onboarding should surface these IMPLICITLY by asking concrete questions, then SYNTHESIZE a strawman profile the user reacts to.

---

## The methodology insight

**Industry-fluid is acceptable. Capability-fluid is not.**

Founders genuinely can be domain-flexible (don't care if it's dental scheduling or HVAC dispatch — both work for them). They cannot be capability-flexible (a solo engineer with no capital cannot run an enterprise sales motion; an iOS-only distributor cannot sell B2B contracts to enterprises).

The onboarding's job is to:
- Accept domain-fluidity (no forced "what industry do you want")
- Lock in capability filters (these are real, immutable for the engagement)
- Surface implicit capabilities the user takes for granted (licenses, accesses, fluencies)
- Push back firmly on "I'll adapt" without being preachy

The synthesized profile encodes both: domain-flexibility ("scan widely") + capability-rigidity ("filter by these specific feasibility constraints").

---

## Proposed solution

### New command: `/research-init`

**Frontmatter:**
```yaml
---
description: One-time founder profile onboarding. Captures profile, constraints, familiar domains, acquisition channels, and platform assets. Writes to .claude/market-research.local.md so subsequent commands can read context without re-prompting.
argument-hint: (no args — interactive)
---
```

**Body structure (agent-directive):**

The command body instructs the orchestrator Claude to walk the user through 6-8 focused questions using `AskUserQuestion` with multiple-choice options where possible. Each question is small, concrete, and surfaces one signal.

Recommended question sequence:

1. **Role + experience** — multiple choice: "Solo software engineer", "Solo non-technical founder", "Founder + technical co-founder", "Founder + non-technical co-founder", "Other (custom)".
2. **Capital position** — multiple choice: "Bootstrapped, no capital", "Bootstrapped, can spend up to $X/mo", "Funded with runway >12 months", "Funded with runway <12 months". $X to be elicited if option 2.
3. **Time investment** — multiple choice: "Nights and weekends only", "Half-time", "Full-time, 4-week horizon", "Full-time, 8-12 week horizon", "Full-time, 6+ month horizon".
4. **Platform / channel accesses you ALREADY have** — multi-select: "Apple Developer license", "Google Play developer account", "Chrome Web Store developer account", "GitHub presence with >500 followers", "Twitter/X audience with engagement", "Existing newsletter subscribers", "Industry-specific certifications or licenses", "None of these".
5. **Acquisition channels you're WILLING to do** — multi-select: "Cold outbound (DMs, email)", "Build-in-public on Twitter/X", "Long-tail SEO content", "App Store organic", "Community participation (Discord, forums)", "Friend/network introductions", "Conference talks or appearances", "Paid ads (if budget allowed)", "Enterprise sales motion (if team supported)".
6. **Industries or problem areas where you have personal insight** — open text, with explicit examples. Frame as "industries where you've personally felt pain, sold something, or have meaningful network." Skip is allowed (with the pushback framing).
7. **Pricing models you'd ship** — multi-select: "Monthly SaaS subscription ($X-$Y/mo)", "One-time App Store purchase ($X-$Y)", "Usage-based / metered ($X per unit)", "Annual contract ($X+/yr)", "Open to any of the above".
8. **Anything else load-bearing the agent should know** — open text, optional. Things like "I have a co-founder agreement that requires equity", "I won't relocate", "I have a medical issue that limits travel", etc.

**Step 2: Synthesize a strawman profile.**

After all questions, the orchestrator Claude composes the founder profile + constraints + familiar domains as a paragraph block — the same shape as v0.1.1 expects. The user **reads and reacts**, doesn't write from scratch.

Apply the "industry-fluid is fine, capability-fluid is not" rule when the user skips question 6 — synthesize familiar domains from their licenses + acquisition preferences + role.

**Step 3: User reviews and adjusts.**

Use AskUserQuestion with options: "Looks good, save it", "Adjust founder profile", "Adjust constraints", "Adjust familiar domains", "Adjust acquisition channels". Iterate until "looks good."

**Step 4: Write to `.claude/market-research.local.md`.**

File format:

```markdown
---
schema-version: 1
founder-profile: |
  [synthesized founder profile paragraph]
founder-constraints: |
  [synthesized constraints paragraph]
familiar-domains: |
  [synthesized familiar domains paragraph]
acquisition-channels: [list]
platform-assets: [list]
last-updated: 2026-05-19
---

# Market Research Profile

[Human-readable expanded version of the synthesized profile, for the user to re-read later.]
```

YAML frontmatter is machine-readable; markdown body is human-readable. Subagents read the frontmatter; the user reads the body.

### Updates to existing seven commands

Each command's Step 1 must be updated to:

1. **Read `.claude/market-research.local.md` first** (via `Read` tool if it exists)
2. **Use the file's `founder-profile`, `founder-constraints`, `familiar-domains` as defaults**
3. **Fall back to AskUserQuestion only for inputs not in the file** (or if the file is absent)
4. **Always prompt for command-specific inputs** (codebase path for `/research-icp-audit`; named angle for `/research-pressure-test`) — those are per-engagement, not per-founder

### Settings file pattern reference

Per `plugin-dev:plugin-settings`, the convention is `.claude/<plugin-name>.local.md`. For us: `.claude/market-research.local.md` in the user's project directory (NOT in the plugin install dir — the file lives where the user works).

## Implementation sketch

Roughly 4-6 tasks, following the established T4-T9 pattern:

- **Task 1:** Write the new command file `commands/research-init.md` (agent-directive style; orchestrates the 8 questions + synthesis + save)
- **Task 2:** Optionally create a small init-agent if the orchestration logic gets complex enough to warrant isolation. Likely NOT needed for v0.1.2 — Claude can handle the 8-question + synthesis flow inline without a separate subagent.
- **Task 3:** Update each of the 7 existing commands to read `.claude/market-research.local.md` in Step 1 with AskUserQuestion fallback. Repetitive but mechanical.
- **Task 4:** Update SKILL.md's Phase-to-command map to mention `/research-init` as a one-time prerequisite (not a phase, but a setup command).
- **Task 5:** Update README with the new init flow + an example `.claude/market-research.local.md` file structure.
- **Task 6:** Bump version to 0.1.2 in manifest + README footer. Tag v0.1.2.

Estimated time: 3-4 hours given the established subagent-driven-development pattern.

---

## Acceptance criteria

- [ ] User can run `/research-init` once and answer 6-8 focused questions
- [ ] Output is a synthesized profile the user reacts to (not free-form prose the user writes)
- [ ] Result is saved to `.claude/market-research.local.md` with both YAML frontmatter (machine-readable) and markdown body (human-readable)
- [ ] All 7 existing commands read this file before falling back to AskUserQuestion
- [ ] If the file is absent or stale (>6 months), commands still work via the original AskUserQuestion path
- [ ] The "industry-fluid is fine, capability-fluid is not" framing appears in the command body so the orchestrator pushes back on "keep it open" answers consistently
- [ ] Apple Developer license and similar implicit capabilities are surfaced by question 4 (multi-select), not by free-form prose
- [ ] Plugin-validator passes on the new structure
- [ ] Live smoke test: a user with no existing `.claude/market-research.local.md` who runs `/research-init` then `/research-demand-discovery` should not be re-prompted for founder context in the second command

---

## Out of scope for v0.1.2

- **Per-project profile vs per-user profile.** v0.1.2 writes to the user's CURRENT project directory. Multi-project profile sharing is v0.2.
- **Profile evolution / amendment workflow.** v0.1.2 supports re-running `/research-init` to overwrite the file. Smarter amendment (e.g., "I just got an Apple Developer license, update only that field") is v0.2.
- **Founder profile templates / examples.** v0.1.2 doesn't ship pre-baked profile templates ("solo iOS dev", "ex-FAANG technical co-founder", etc.) — those are nice-to-have for v0.2.

## Notes from the engagement that surfaced this spec

The user's first attempt at providing founder profile in v0.1.1:

> "I am a heavy user of claude code and have delegated almost all of my work to agents for me. I am willing to work any amount of time to finally generate that sweet source of income using my skills as a software engineer. I have no funding right now, I want to build something and make money with it. I am a solo developer, but comfortable with managing a team of agents to multiply my work output. 2. My current contraint is having starting capital to invest in services, maybe a few are acceptable for an appropriate tech stack. I have apple developer license. Go cheap and broad"

What was missing:
- Familiar domains (entirely omitted)
- Acquisition channels (not addressed)
- Time horizon for MVP (vague — "any amount of time")
- Pricing model preference (not addressed)

When prompted for the missing items, the user's response:

> "I didn't mention familiar domains because I want to keep the search open and I can adapt to whatever problem we find to solve. I guess I am very familiar with AI agentic workflows but as a dev pipeline, not tied to it as product scope. 2. I am not sure about aquisition"

This is the canonical case for the v0.1.2 onboarding. The user is being honest — they don't know. The onboarding's job is to STRUCTURE the unknowns into a usable input set, not demand the user produce one from scratch.

After pushback and a synthesized strawman, the user accepted with "Looks good, let's dispatch." That synthesize-and-react pattern is the v0.1.2 UX target.
